**依頼者**：芝野さん　**引き継ぎ先**：【0301】LOOM アーキテクチャ可視化

## 1. 何に気づいたか（芝野さんの言葉）

> ノードって、「システムとか人間みたいなもの」を書くべきだと思うんですよね。
> 逆に言うと、**情報やアウトプットってノードに書くべきものじゃない**と思ったんですよね。
> でも、Loomの可視化には必要なものだと思うんですよね。

そのうえで、こう提案されています。

> 多分、「ノードの間を移動するもの」「ノードの処理で生み出されるもの」
> 「ノードの処理で価値が変わるもの」このようなものを一旦『**アウトプット**』と呼んでおきましょうか。
> タスクフローの処理の中で、ノード上でアウトプットが生み出されたり、ノード間の移動とか、
> ノード上で別のアウトプットに変化するとか。こんな感じで、**『アウトプット』の状態遷移を管理すれば**
> いいと思ったんですよね。状態をきちんと定義できたら、**Reactの描画でそれっぽいアニメーション**で
> 表現できますよね。

## 2. 実データが、そのとおりになっている

`samples/*.json` 全体のノード型の内訳（117ノード）：

| 型 | 数 |
|---|---|
| backend | 35 |
| **storage** | **32** |
| agent | 31 |
| human | 12 |
| frontend | 7 |

**`storage` の32個を開くと、はっきり2種類に分かれる。**

| | 例 |
|---|---|
| **置き場（主体）** | Secret Manager / BigQuery / S3 / DynamoDB / PostgreSQL / Google Drive / Google Sheets / GitHub / YouTube / GCS |
| **成果物（アウトプット）** | structure.json / images/ / audio/narration.wav / output.mp4 / ビルド成果物 |

極端な例：
- `receipt-automation-pipeline.json` … storage 2個とも**置き場**（Google Drive / Sheets）
- `product-intro-pipeline.json` … storage 4個とも**成果物**（structure.json / images/ / narration.wav / output.mp4）

**同じ型に入れるものではなかった。**

今日 S-11 用に作った `voice-clone-pipeline.json` も同じで、
主体（だいき・録音アプリ・Claude Code・Colab・A100・RTX 3050）と
成果物（音声1,013本・モデル4.3GB・合成した音声・紹介動画）を、同じ平面に並べていた。

## 3. 現状の構造（`src/types.ts`）

```ts
export type ArchNodeType = "human" | "frontend" | "backend" | "agent" | "storage" | "spacer";

export interface Task {
  id: string; label: string; description: string;
  mainNode: string;        // このタスクが動くノード
  inputNodes: string[];    // 入力を供給するノード
  outputNodes: string[];   // 出力を受け取るノード
}
```

**`inputNodes` / `outputNodes` が「ノード」を指しているのが、いまの設計の芯。**
アウトプットをノードとして置かないと、タスクの入出力が表現できない作りになっている。
ここを変えると、`flow` の意味づけも変わる。

## 4. 設計の論点（決めていない。0301 で詰めるもの）

### (a) 「価値が変わる」とき、同じものか、別のものか

芝野さんの3つめ「**ノードの処理で価値が変わるもの**」が、いちばん効くところだと思います。

- `narration.wav` が字幕と合成されて `output.mp4` になる ── これは**別物になった**のか、
  **同じアウトプットの状態が変わった**のか
- 前者なら「アウトプットAが消えてBが生まれる」、後者なら「Aの状態が遷移する」

**ここの決め方で、データモデルも、アニメーションの見え方も変わります。**
同一性を保つなら「1本の線がノードを渡り歩く」絵になり、別物なら「生まれて消える」絵になる。

### (b) 置き場をどうするか

`storage` の置き場のほう（S3、BigQuery）は**主体として残す**のが自然に見えます。
そうすると `storage` 型は「置き場」専用になり、成果物は型ではなく**別の概念**になる。

ただし「Google Drive」のように、**置き場そのものが成果物の所在を表している**ケースもあるので、
「アウトプットがどのノードの上にあるか」で表せるなら、置き場ノードが要らなくなる場面もあるはず。

### (c) 既存ドキュメントの移行

`samples/` に12本ある。`normalizeLoomDocument` が v1→v2 を吸収している前例があるので、
**v2→v3 も同じやり方で、成果物っぽい storage を自動でアウトプットに寄せられる**かもしれない。
ただし置き場と成果物の自動判別は難しいので、**手で直すほうが早い**可能性もある。

### (d) note 挿絵ビューでどう表すか ← 見落としやすい

**アニメーションが使えない場所がある。** `src/components/NoteView.tsx` と
`src/export/renderNoteSvg.ts` は、**静止画の PNG を書き出すための経路**。

状態遷移をアニメーションで表現する設計にすると、
**note 挿絵では「あるステップの瞬間」を切り取る**ことになる。
ステップごとに書き出す仕組み（全ステップ一括ZIP）は既にあるので、
**各ステップで「どのアウトプットがどこにあるか」が静止画でも分かる**必要がある。

これは実際に S-11 で使った機能なので、壊すと note の挿絵が作れなくなる。

### (e) 1つのタスクで複数のアウトプットが動くとき

いまの `outputNodes: string[]` は複数を許している。
アウトプットが第一級になると、「このタスクはAを生み、Bを動かし、CをDに変える」が
同時に起きうる。**タスク1つに対して遷移を複数持たせる**形が要りそう。
