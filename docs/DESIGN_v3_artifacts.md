# Loom v3 設計：ノード・ツール・アーティファクト（2026-11-07 時点）

発端と構想は [HANDOFF_outputs.md](HANDOFF_outputs.md)。この文書は、芝野さんとの要件の詰めで**決まったこと**と、**まだ決めていないこと**を書く。実装はまだしていない。

## 1. 考え方

図に出てくるものを、文の役割で分ける。ArchiMate（The Open Group の企業アーキテクチャ記法）が要素を主語・動詞・目的語にたとえているのにならう。

| 文の役割 | Loom の要素 | 例 |
|---|---|---|
| 主語 | **ノード**（主体） | だいき、Claude Code、Colab、BigQuery |
| 動詞 | **タスク** | 作る、渡す、保管する |
| 目的語 | **アーティファクト** | 音声1,013本、モデル、output.mp4 |
| 「〜を使って」 | **ツール**（道具） | 背景を透明にする関数、学習済みモデル |

タスクは「ノードが、ツールを使って、アーティファクトをどうするか」を1文で書いたもの。言い換えると、**タスクは3種類の要素の状態変化を記述したもの**。

**理由**：これまでは成果物（structure.json、output.mp4 など）もノードとして置いていた。サンプル12本の `storage` 型32個は、置き場（S3、BigQuery）と成果物に割れていた。人が書いても Claude が書いても主体と成果物が混ざらないように、構造として分ける。

## 2. 用語

| 日本語（会話） | データ | 画面の表示 |
|---|---|---|
| 主体 | `node` | ノード |
| タスク | `task` | タスク |
| 道具 | `tool` | ツール |
| アウトプット | `artifact` | アーティファクト |

- **node / task** は v2 のデータ名（`architecture.nodes`、`flow.tasks`）をそのまま使う。変えると全サンプルの書き換えが要るため。
- **step** は使わない。Loom では「再生の今の位置」の意味ですでに使っている。**process** はタスクの集まり全体（プロセスフロー）の意味で使っている。
- **tool** にした理由：function だとモデルやスクリプト全体が入らない。
- **artifact** にした理由：output だと「次のタスクの入力として使う output」と書くことになり紛らわしい。v2 の `inputNodes` / `outputNodes` ともぶつかる。object は JavaScript のオブジェクトと区別がつかない。artifact は入力でも出力でも使え、UML・ArchiMate でも成果物はこの名前。画面も「アーティファクト」にそろえる（芝野さんの判断。最近よく聞く言葉になってきたため）。

## 3. 決まったこと

### 3.1 ノードとツールの境目

- **迷ったらノードに寄せる。ツールは無理に使わない。**
- BigQuery、S3、Google Drive などの**置き場はノード**（データを保管する主体）。
- ツールを使うのは、「作られたあとに、別の主体の上で働く」ものを見せたいとき。例：Colab で作ったモデルが RTX 3050 の上で音声を合成する。

### 3.2 ツール

- **必ず1つのノードに載る。** 同じものを2か所で使うなら、別のツールとして2つ定義する。
  - 理由：同じツールを複数の場所で使う具体例が思いつかなかった。持ち方が単純になる。
- **見せ方：ノードの中にセット・アタッチする表現**（ノードとは別の見た目）。
  - 理由：「ノードがツールを使う」という文と見た目が一致する。ノードのマス目を使わないので配置が崩れない。note の挿絵（静止画）でも、そのステップで付いているツールが札として残るので表せる。
  - ツールは作られる場面ではアーティファクトとして生まれる。行き先のノードに着いたらツールとして装着される、という見せ方ができる（演出は未決）。

- **データの形（試作で実装）**：ツールは別の種類の要素ではなく、**アーティファクトに `"tool": true` を付けたもの**。
  - 運ばれている間はふつうの札として線に沿って動き、ノードに落ち着いたらノードに装着された帯（レンチの印）として描く。
  - 使うときは、derive などの対象（`artifacts`）に入れるだけ。ツールは減りも変わりもしない。使われたステップでは帯が強調される。
  - 最初から装着されているツールは `at` で置く。
  - 例：音声クローンの「モデル 4.3GB」。A100 で作られ（アーティファクト）、RTX 3050 に降ろされ、そこで音声合成に使われる（ツール）。

### 3.3 アーティファクト

- **かたちが変わるとき**、別物になるのも状態が変わるのも**区別しない**。元のアーティファクトが役目を終え、新しいアーティファクトが生まれる形にそろえる。アーティファクトに「状態」の項目は持たせない。
  - 引き継ぎ書の「ノードの処理で価値が変わるもの」は「**かたち**が変わるもの」の打ち間違い（芝野さん確認済み）。
- **消える**ことは基本的に扱わない。アーティファクトは残り続ける。個人情報の削除など、消すことに意味がある場面のためだけに「捨てる」を残す。
- **読むだけ**（試作で追加）：`keep: true` は「受け取る」にも付けられる。元は相手のノードに残り、写しが自分へ飛んで消える。例：BigQuery の記録を読む、GPU の仕様を調べる。
- **渡す**は、基本は**移動**（元のノードからなくなる）。アーティファクトは常にどこか1か所にある。
  - コピーが説明上重要なときだけ、明示的に残す。「元を参考にして、新しいアーティファクト（コピー）を作る」と書けば表せるので、コピー専用の仕組みは要らない可能性がある。

### 3.4 表示

- **これまでに生まれたアーティファクトは、すべて今ある場所に表示する。** 今のステップで動いたものは強調する。
  - 理由：並行タスクが合流する場面では、全部見えていたほうが分かる。
- アーティファクトの「今ある場所」は、再生でたどった道筋に沿って計算する。分岐で選ばなかった側のアーティファクトは出てこない。

### 3.5 タスクとアクション

- **タスクは主語のノードを1つ持つ。** 1つの文に主語は1つ、という考え方。
  - 受け渡しのときの主語は、**その処理を実際に動かしている側**。例：Cloud Run が GCS から画像を取ってくるなら Cloud Run。GCS が通知を送るなら GCS（押し出すか、取りに行くかの違いが図に残る）。
- **タスクの下に `action` の層を置く。** タスクは action を1つ以上持つ。
  - action は、アーティファクトの1つの変化。類型（生み出す、渡す、かたちを変える…）、対象のアーティファクト、相手のノード（取り出し元・渡し先）、使うツール（あれば）を持つ。
  - 先例：UML のアクティビティ図も、アクティビティの中に、それ以上分けないアクションが並ぶ2段構え。
- **タスクの切り方**：主語が変わったら**必ず分ける**。同じ主語でも、見る人に一度立ち止まって見てほしいときは**分けてもよい**（書き手の判断）。
  - 理由：1タスク1変化にすると、再生の回数が増え、プロセスフロー図にタスクが並びすぎて流れの形が見えにくくなる。
  - 先例：BPMN もタスクは1つのレーン（担当者）に属し、担当者が変わるところで分かれる。
- **類型の棚卸しは action に対して行う。** タスクの種類ではなく、action の種類を有限個に絞る。
- 再生では action を順に動かす。note の挿絵（静止画）では、タスクが終わった時点の状態を描く。

例：

```
task: 「B が X を加工して C に渡す」 主語 = B
  action 1: 受け取る       X を A から
  action 2: かたちを変える  X → Y（ツール: 変換関数）
  action 3: 渡す           Y を C へ
```

- 同じ主語の中の action は、たいてい「受け取る → 変える → 渡す」の順に並ぶ。v2 のタスクの「入力ノード → 軸ノード → 出力ノード」と同じ形（気づいた点。標準形にするかは未決）。

### 3.6 データの形（たたき台。キー名は類型の棚卸しのあとで確定）

- **アーティファクトには変わらないことだけを書く。** 今ある場所と、用済みで非表示かどうかは**データに持たせず、再生でたどった道筋の action から計算する**。
  - 理由：どちらも再生のどの時点か（分岐の選択、戻る、途中へのジャンプ）で変わる値。データに書くと、どの時点の値かが決まらない。今の Loom がタスクの強調を位置から計算しているのと同じ考え方。
- **action の主語はタスクから引き継ぐ。** action ごとに主語のノードを書かない（同じことの二重書きと食い違いを避ける）。action に書くのは相手のノード（`from` / `to`）だけ。
- **action は類型（`type`）と、前後のアーティファクト（`artifacts` / `results`）で書く。** 「用済み」になるかは類型から決まる。
- **`artifacts` と `results` はどちらも配列。** 1つの action で、複数を生み出す（create → results 複数）、複数から複数を作る（derive / transform → artifacts 複数・results 複数）、複数を一度に渡す、を書ける。
  - derive は対象がすべて残り、結果がすべて主語のノードに生まれる。transform は対象がすべて役目を終える。
  - 「ラベルが書き換わる演出」（3.10）は、元と結果が1対1のときだけ。それ以外は、元が消えて（transform）／残って（derive）結果が現れる見せ方。
  - 「音声1,013本」のように多数をひとまとまりで扱うかは書き手の判断（1つのアーティファクトにまとめてよい）。
- キー名はキャメルケース（v2 の `mainNode` などに合わせる）。`from` / `to` はアーキテクチャのエッジと同じ「どこからどこへ」の意味。

```jsonc
"artifacts": [
  { "id": "voices", "label": "音声1,013本", "at": "daiki_pc" },  // at = 最初からある場合の置き場所
  { "id": "model",  "label": "音声モデル" },                      // at なし = どこかのタスクで生まれる
  { "id": "tick",   "label": "8:30 の合図", "transient": true }     // 受け取られたら消える
],
"tasks": [{
  "id": "task_3", "label": "B が X を加工して C に渡す", "node": "B",
  "actions": [
    { "type": "receive",   "artifacts": ["x"], "from": "A" },
    { "type": "transform", "artifacts": ["x"], "results": ["y"], "tool": "converter" },
    { "type": "send",      "artifacts": ["y"], "to": "C" }
    // 手元に残して写しを渡す: { "type": "send", "artifacts": ["y"], "to": "C", "keep": true }
  ]
}]
```

| 類型（たたき台） | artifacts（対象） | results（結果） | 用済みになるもの |
|---|---|---|---|
| create（生み出す） | なし | 新しいもの | なし |
| receive / send（受け取る／渡す） | 動かすもの | なし（同じものが移る） | なし（`keep: true` の send は写しが届いて消える、3.9） |
| transform（かたちを変える） | 元 | 新しいもの | 元 |
| derive（参考にして作る） | 参考にするもの | 新しいもの | なし（元は残る） |
| inspect（確かめる） | 見るもの | なし | なし（判断のタスク、3.7） |
| discard（捨てる） | 捨てるもの | なし | 対象 |

### 3.7 判断のタスク

- 判断（承認ゲート、判定、レビュー）は、**判断する側にアーティファクトが届いて、それを見る**と解釈する。サンプルの判断タスク12個のうち11個は、届くもの（台本、画像、下書き、抽出データ、回答記録など）がはっきりしていた（残り1つは「調べて事実が分かった」話で、判断ではなかった）。
- action は「受け取る」＋「確かめる」（見るだけ。元は残り、何も生まれない）。分岐は v2 と同じく、タスクのつながり（`connections`）で表す。
- **判断の結果を図に出したいときは、ふつうのアーティファクトとして作る**（例：「判定結果」「承認済みの台本」）。判断の結果のための特別な見た目（ラベル、札の種類）は作らない。
  - 理由：ふつうのアーティファクトの見た目で識別できれば足りる。見た目の種類を増やさない（3.12 の原則）。

### 3.8 起動・呼び出し・合図

- イベント、トリガー、リクエスト、時刻の合図も**アーティファクトとして書く**。例：「push された」通知、「8:30 になった」合図、アップロードのリクエスト。
  - 理由：ノードの間を動くものは、すべて同じルールで管理・表示できる。後工程で使わないものでも、何かがノード間を移動する点は同じなので、アーティファクトの移動と同じ見せ方で自然。
- 時刻の合図のように元がないものは、送り出す側のノードが「生み出す」→「渡す」と書く（例：Cloud Scheduler が「8:30 の合図」を生み出してボット本体に渡す）。

- **合図は受け取られたら消える。** アーティファクトの定義に `"transient": true` を書くと、受け取った時点で非表示になる（受け取った側が「捨てる」を書かなくてよい）。
  - 理由：表示は「これまでに生まれたものはすべて今ある場所に出す」（3.4）なので、合図が受け取った側にたまり続ける。合図は数が多く、毎回「捨てる」を書くのは手間と書き漏れの元になる（Claude が書く場合も同じ）。

### 3.9 外部サービスとのやりとり（頼んで、結果を受け取る）

- 「スクリプトが Gemini TTS に台本を渡し、音声を受け取る」のようなやりとりは、**呼び出す側を主語にした1つのタスク**に収める。戻ってくるところは「呼び出す側が受け取る」と書く（受け渡しはどちらを主語にしても同じ出来事、3.5）。
  - 外部サービスはノードのまま、相手のノード（渡し先・受け取り元）として出てくる。ツールにはしない（「迷ったらノードに寄せる」、3.1）。
  - 「頼む」のような新しい類型は作らない。既存の「渡す」「受け取る」を使い回す（芝野さんの判断）。
- **`keep: true`（手元に残す）**：「渡す」に付けると、元のアーティファクトは送り手に残り、**写しが渡し先へ飛んで、届いたら消える**。
  - 例：台本を TTS に渡しても、手元の台本は後で字幕に使う。
  - 消えるかどうかはアーティファクトの性質ではなく**渡し方**で決まるので、`transient` ではなく action 側の指定にする。
  - 何も書かなければ移動（3.3）。手元に残したいときだけ明示する。書き忘れても図が散らからない側に倒れる。
  - 同じ形の例：Claude に設計書を読ませる、API に設定を送る、BigQuery の記録を読んでエージェントに渡す。

```
task: 「ナレーション生成」 主語 = スクリプト
  action 1: 渡す（keep）  台本 を Gemini TTS へ
  action 2: 受け取る      音声 を Gemini TTS から
  action 3: 渡す          音声 を GCS へ
```

### 3.10 その場の書き換え

- structure.json に字幕を書き戻す、ステータスを更新する、などは「かたちを変える」で書く。結果のアーティファクトに、書き換えたあとのラベルを付ける（例：`structure` → `structure_captioned`「structure.json（字幕つき）」）。
- 元と結果が同じノードにあって1対1で変わるときは、**ラベルが書き換わる演出**で見せる。
- 理由：仕組みを増やさずに済み、「アーティファクトに状態を持たせない」（3.3）を守れる。「いつからどのラベルか」もデータに残る。

### 3.11 ノード自体の状態の変化（今は扱わない）

- 「稼働開始」「API サーバー起動」「配信準備完了」のような、ノードが動き出す・状態が変わる話は、**今は考慮しない**（芝野さんの判断）。
- 書く必要があるときは、そのきっかけになったアーティファクトが届くところまでで表す（例：コンテナが EC2 に届く）。

### 3.12 全体の原則

- **正確さより見た目の単純さを優先する。** 現実のデータの動き（コピーが残る、など）より、図として分かりやすいほうを選ぶ。説明の文脈で正確さが重要な場面だけ、明示的に書く。

## 4. まだ決めていないこと

1. ~~**action の類型**~~ → 2026-11-07 にサンプル98タスクで棚卸し済み。3.6 の表（create / receive / send / transform / derive / inspect / discard）と、3.7〜3.11 の扱いで確定。キー名は試作で最終確認する。以下は棚卸し前のメモ：action を有限の類型に棚卸しし、可視化をその類型に合わせる（3.5 で、類型はタスクではなく action に付けると決めた）。会話で出た動詞の候補：
   - 生み出す（元になるものはない）
   - 渡す／受け取る（ノード間の移動。どちらを主語にしても同じ出来事）
   - かたちを変える（元が役目を終え、新しいものが生まれる）
   - 保管する（置き場のノードにとどまる。「渡す」の行き先が置き場の場合とも言える）
   - 参考にして作る（元は残り、新しいものが生まれる。1つまたは複数）
   - 捨てる（個人情報など、意味がある場面だけ）
   - 「参考にして作る」と「かたちを変える」を区別するかは未決。3.3 で消えることを基本扱わないと決めたので、区別の必要は薄れている。
2. **note の挿絵（静止画）での見せ方**：アーティファクトとツールを、ステップの瞬間の静止画でどう描くか。全ステップの一括書き出し（ZIP）は既にある。S-11 で実際に使った機能なので壊さない。
3. **既存サンプル12本の移行**：v1→v2 の `normalizeLoomDocument` の前例にならうか、手で直すか。置き場と成果物の自動判別は難しい。
4. ~~1つのタスクで複数のアーティファクトが動くときの書き方~~ → 3.5 の action の層で解決。
5. **v2 の `inputNodes` / `outputNodes` の扱い**：アーティファクトの移動で置き換えるのか、残すのか。
6. **アニメーションの演出**：アーティファクトの移動、生成、装着の見せ方。

7. **途中へのジャンプ**：フロー図のタスクをクリックして途中に飛ぶと、どの道を通って来たかが分からず、アーティファクトの場所を決められない。「最初から、分岐ではいつも同じ側を選んで進んだ道」を仮に使う、などの決めごとが要る。
8. **編集の UI**：考え方の芯は「編集する人はアーティファクトの場所を直接動かさない。編集するのは action だけで、場所は計算される」。タスクの編集画面に、直前の時点の配置を表示し、action の対象を図の上でクリックして選ぶ（v2 の「アーキテクチャから選択」と同じ操作）形が候補。具体的な姿は試作のあとで決める。

## 4.0 試作で分かったこと・決まったこと

- **アニメーション**：今のステップで起きた変化（移動・誕生・役目を終える・写しや合図の飛行）を、そのステップを表示している間**ループ再生**する（芝野さん依頼）。
- **移動の道筋**：1つのタスクの中で通ったノードを順番にたどり、ノード間は**アーキテクチャの線をたどる最短の道筋**を通る（線がなければ直線）。生まれてすぐ渡されるものは、生まれた場所に現れてから動く。
- **note 挿絵の込み具合**：札が3つ以上たまるノードでは札が下の段まで伸び、ラベルも省略される（38px のため）。ツールの帯もラベルが省略されやすい。要検討。

- **込み合ったときの表示（2026-11-08 決定、いつもの表示）**：試験用サンプル（`samples/stress-artifacts-v3.json`：ツール5つのノード、札が5つたまる置き場）で比べて決めた。
  - ツールは、ノードの下半分に**小さなレンチのアイコン**として横に並べる（名前はカーソルを乗せると出る）。帯で積むと2つ目からノードのラベルを隠したため。
  - 今のステップで**同じ action・同じ扱い・同じ場所から**扱われたアーティファクトは、**1つの札にまとめて「画像 12枚 ほか2件」**と出す（一緒に飛ぶ写しも1枚で飛ぶ）。「今動いたものは必ず見せる」と「込み合わない」を両立させるため（案 B）。
  - そのうえで、1つのノードの札は**2つまで**。超えた分は「+N」にまとめる（今のステップで扱ったものを優先して見せる）。
  - 札が少ないときは、まとめない表示と見た目が同じなので、切り替えは設けない。
- **action の説明**：action に任意の `label` を書ける。書かなければ類型・アーティファクト・相手のノードから文を作る（ツールは「〜を使って」、`keep` は「（写し）」）。アーキテクチャ図の左上に番号つきで並べ、アニメーションと同じ時間で、今再生している action を強調する。
- **タイミング**：action を順番に再生（1つ 1.3 秒＋間 0.4 秒、最後に 1 秒止まってループ）。同じ action の中の複数のアーティファクトは同時に動く。使われただけ（参考・確かめる・写しの元）は時間を延ばさない。

## 4.1 進め方（2026-11-07 合意）

1. action の類型を棚卸しする
2. **編集画面なしで試作する**：データの形と表示（アーティファクトの札、再生に合わせた移動、note の挿絵）だけを実装し、JSON は Claude が書く
3. 音声クローンの図（`samples/voice-clone-pipeline.json`）を新しい形に書き直して動かし、**分岐・並行での見え方**と画面の込み具合を確かめる（芝野さんが不安に感じている点）
4. 実物を触ったうえで、編集の UI を考える
